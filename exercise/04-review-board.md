# ส่วน B: คณะกรรมการรีวิวสถาปัตยกรรม (ประมาณ 25 นาที, กลุ่มละ 4 คน)

> **เชื่อมโยงกับการบรรยาย:** AICH4 (การรีวิวต้องอาศัยความเชี่ยวชาญในโดเมน; *ฟังดูดี ≠ เหมาะสม*), Pillar 5 (AI เป็น Chief Analyst มนุษย์เป็น Chief Strategist), JSS (85% ของงานวิจัยให้มนุษย์มีส่วนร่วมในกระบวนการ)
> **คำถาม:** คณะกรรมการที่เป็นมนุษย์จับประเด็นใดได้ที่ผลรีวิวของ AI พลาดไป และเพราะเหตุใด

คณะกรรมการรีวิวสถาปัตยกรรมของบริษัทประชุมเพื่ออนุมัติการออกแบบ R-12 ก่อนเทศกาลลดราคา 11.11 โดยนำ ADR หนึ่งฉบับเข้าที่ประชุม **สถาปนิก**นำเสนอ ADR, **AI analyst** นำเสนอผลรีวิวของ AI และผู้มีส่วนได้ส่วนเสียสองคนนำข้อมูลที่ AI ไม่เคยเห็นมาด้วย

## 1. จัดตั้งคณะกรรมการ (2 นาที)

ในกลุ่มละ 4 คน ให้เลือก ADR ของสมาชิก**หนึ่งคน**มารีวิว (`docs/adr/0002-*.md` พร้อม `exercise/outputs/3-review.md` ของคนนั้น) แล้วแบ่งบทบาท

| บทบาท | ใคร | สิ่งที่นำมา |
|---|---|---|
| **สถาปนิก** | ผู้เขียน ADR | ปกป้อง ADR |
| **AI analyst** | | อ่านผลรีวิวของ AI เท่านั้น ห้ามใส่ความเห็นของตัวเอง |
| **Product owner** | | การ์ดบทบาท P (ฝั่งธุรกิจ) |
| **Site reliability engineer (SRE)** | | การ์ดบทบาท S (ฝั่งปฏิบัติการ) |

กลุ่มละ 5 คน ให้เพิ่ม**เจ้าหน้าที่ความปลอดภัยและความเป็นส่วนตัว** (การ์ดบทบาท X) กลุ่มละ 3 คน ให้สถาปนิกรับบท AI analyst ด้วย

**การ์ดบทบาท**อยู่ใน [`docs/review-board/`](../docs/review-board/README.md) ผู้มีส่วนได้ส่วนเสียแต่ละคนอ่าน**เฉพาะการ์ดของตัวเอง** และเก็บเป็นความลับจนถึงเวลาประชุม

## 3. บันทึกผลการตัดสินใจ (8 นาที, ทำร่วมกัน)

**ที่มา:** [`exercise/04-review-board.en.md` ใน repo เพื่อนกลุ่มเดียวกัน](https://github.com/RATSAPORN/swarch-ai4swarch/blob/main/exercise/04-review-board.en.md) (ผู้ใช้ยืนยันว่าเป็นกลุ่มเดียวกันและเพื่อนอนุญาตให้คัดลอก; AI แปล/จัดรูปเป็นภาษาไทย). รายละเอียดการประชุมต่อไปนี้อิงบันทึกเพื่อน ไม่ใช่คำยืนยันว่าผู้เรียนได้พูด ตรวจ หรือรับรองเอง

**ADR ที่กลุ่มเลือกรีวิว:** [`docs/adr/0002-myadr.md` ของ Ratsaporn](https://github.com/RATSAPORN/swarch-ai4swarch/blob/main/docs/adr/0002-myadr.md) (ผู้ใช้ยืนยัน). บันทึกเพื่อนใส่ชื่อหลัง “by” ต่างกัน 5 ชื่อ จึงคงรายละเอียดรายคนไว้ตามต้นฉบับ

**สมาชิกและบทบาทตามบันทึกเพื่อน:**

| บทบาท | ผู้ที่บันทึกระบุ |
|---|---|
| สถาปนิก | Ratsaporn |
| AI analyst | Weeraphat (ผู้ใช้ระบุชื่อไทยว่า วีรภัทร เลิศเจริญวรกุล; บันทึกเพื่อนมีเพียงชื่ออังกฤษ) |
| Product owner | Poonyapat |
| Site reliability engineer (SRE) | Boonchai |
| เจ้าหน้าที่ความปลอดภัยและความเป็นส่วนตัว | Rachata |

**มติที่บันทึกแยกรายการ:**

| ชื่อหลัง “by” / บทบาทที่บันทึก | มติที่บันทึก |
|---|---|
| Rachata / security & privacy officer | accept with changes |
| Boonchai / SRE | accept with changes |
| Poonyapat / Product owner | accept with changes; มีข้อความ “/ accept with changes / reject” ค้างในต้นฉบับ จึงไม่ถือเป็นมติอีกครั้ง |
| Weeraphat / AI Analyst | accept |
| Ratsaporn / Architect | accept |

**สิ่งที่ต้องแก้ตามบันทึกรายคน:**

| ผู้บันทึก | รายการ |
|---|---|
| Rachata | (1) แยก schema ของ email, loyalty และ analytics พร้อมระบุข้อมูลส่วนบุคคลแต่ละข้อความ; อย่ากระจายข้อมูลลูกค้าทุก consumer. (2) ตัดอีเมล/ชื่อเต็มออกจาก analytics และประเมินว่า `orderId` เชื่อมกลับหาตัวบุคคลได้หรือไม่. (3) จำกัดสิทธิ์แต่ละคิว รวม retry/dead-letter ให้ service และผู้ดูแลเท่าที่จำเป็น |
| Boonchai | (1) แก้สมมติฐานทักษะ: สองคนเคยใช้ RabbitMQ บน laptop เท่านั้น; ยังใหม่กับ production และมีคน on-call สองคน. (2) ให้ dashboard, alert, backup และ runbook เป็นเงื่อนไขก่อนปล่อยระบบ; ต้นฉบับเสนอใช้ราวหนึ่งสัปดาห์. (3) ระบุผู้รับ alert และขั้น escalation/กู้คืนสำหรับ broker, relay, consumer และ storage |
| Poonyapat | (1) หน้า confirmation ต้องแสดงแต้มจริงที่บันทึกแล้ว. (2) “Points pending” หรือ “ภายในหนึ่งนาที” ไม่ตรงคำสัญญาแคมเปญ. (3) กำหนดทางออกเมื่อ loyalty ใช้ไม่ได้และความขัดแย้งกับเงื่อนไขให้ checkout ใช้ได้ต่อ |

**ใครยกประเด็นใด:** คงค่า `Yes` จากบันทึกเพื่อน และแยกผลที่ AI ตรวจเทียบกับ [AI review ของ `0002-myadr.md` ใน repo เดียวกัน](https://github.com/RATSAPORN/swarch-ai4swarch/blob/main/exercise/outputs/3-review.md). รีวิวนี้อ้างไฟล์ `0002-myadr.md` ตรงกับ path ในบันทึก; ผู้ใช้ยืนยันว่ากลุ่มเลือก ADR ของ Ratsaporn

| # | ข้อกังวลในบันทึกเพื่อน | ผู้ยกประเด็นตามบันทึก | บันทึกเพื่อน / AI ตรวจเทียบ | AI มีทางรู้ได้หรือไม่ (เหตุผลตามบันทึกเพื่อน) |
|---|---|---|---|---|
| 1 | แต้มซ้ำทำให้เสียเงิน แต้มขาดทำให้ถูกร้องเรียนและผิดคำสัญญาการตลาด; storage, outbox, RabbitMQ และ loyalty ledger เพิ่มความเสี่ยงส่งมอบของทีม 4 คน; ADR มีแผนทดสอบแต่ยังไม่มีผล | Product owner | Yes / บางส่วน: รีวิวกล่าวถึงแต้มซ้ำและยังไม่มีผลทดสอบ แต่ไม่ระบุความเสียหายทางการเงิน | ต้นฉบับเห็นว่าความเสียหายทางการเงินสำคัญจน AI ควรรู้ |
| 2 | broker, outbox และ storage เพิ่มภาระ on-call ให้เวรสองคน | SRE | Yes / บางส่วน: รีวิวกล่าวถึงภาระทีม 4 คน แต่ไม่ระบุเวร on-call 2 คน | ต้นฉบับเห็นว่าอาจกระทบเว็บไซต์ |
| 3 | event ร่วมอาจส่งข้อมูลส่วนบุคคลไป consumer ที่ไม่ต้องใช้ | Security | Yes / ไม่พบ: รีวิวไม่มีข้อกังวลเรื่อง event กระจายข้อมูลส่วนบุคคล | ต้นฉบับเห็นว่าข้อมูลที่ไม่จำเป็นไม่ควรถูกเปิดเผย |
| 4 | payment อาจสำเร็จก่อนบันทึก order แบบ durable | AI Analyst | Yes / พบ: `Risk` แรกระบุ payment/shipping ก่อน durable commit | ต้นฉบับเห็นว่าเป็นปัญหาลำดับ workflow |
| 5 | ต้องระบุขอบเขต delivery guarantee ให้ชัด | Architect | Yes / บางส่วน: รีวิวกล่าวถึง at-least-once, dedup และ exactly-once แต่ไม่ชี้ขอบเขต guarantee ที่คลุมเครือโดยตรง | ต้นฉบับเห็นว่า scope ไม่ชัดทำให้ AI จับเป้าปัญหาไม่ได้ |

**ข้อค้นพบที่ดีที่สุดของ AI ตามบันทึกเพื่อน:** payment/shipping เกิดก่อน durable order commit; ลูกค้าอาจถูกเก็บเงินโดยไม่มี order ที่บันทึก และ outbox ไม่ปิดช่องว่างนี้. AI ตรวจพบประเด็นนี้ใน `Risk` แรกของ [รีวิวเพื่อน](https://github.com/RATSAPORN/swarch-ai4swarch/blob/main/exercise/outputs/3-review.md)

**ข้อค้นพบที่อ่อนที่สุดของ AI ตามบันทึกเพื่อน:** ความต่างกำลังส่งอีเมลเป็นประเด็นจริง แต่ ADR ในบันทึกคำนวณ backlog และระบุงานติดตามไว้แล้ว จึงเพิ่มข้อมูลใหม่น้อย. AI ตรวจพบ sensitivity point เรื่อง backlog ใน [รีวิวเพื่อน](https://github.com/RATSAPORN/swarch-ai4swarch/blob/main/exercise/outputs/3-review.md)

**มติรวมของกลุ่ม:** `accept with changes` สำหรับ ADR ของ Ratsaporn (ผู้ใช้ยืนยัน); มติรายคนข้างต้นคงตามบันทึกเพื่อน
